# DeepSeek V4.1 Flash 单池中的历史、窗口与压缩器布局

这份设计针对 Flash W4A8、BF16 KV、MRV2 和 Mooncake Pull。目标是在同一个原生 BlockPool 上，给随上下文增长的历史和每请求固定的两类状态分别限额，让一个历史块的物理成本等于其有效数据量。对照版本是实验分支 `experiment/dsv41-logical-state-pools` 的 `82dc35b`。

启用时 P 和 D 都传入以下配置。两个状态槽的容量分别由各端的 `deepseek_v41_swa_slots` 和 `deepseek_v41_compressor_slots` 决定，省略时取该端的 `max_num_seqs`。

```json
{
  "enable_deepseek_v41_logical_state_pools": true,
  "enable_deepseek_v41_packed_history": true
}
```

## 一个页号对应哪些字节

每 128 个输入位置构成一个历史块。下表中索引包含 INT8 数据及 FP16 scale。单位均为每个 TP worker 的 KiB。

| 段 | 同一历史块的数据 | 统一步长版占用 | 候选版占用 |
| --- | --- | ---: | ---: |
| A | 1 层未压缩 BF16 KV | 128 | 128 |
| B | 2 层二倍压缩 BF16 KV，各 64 | 128 | 128 |
| C | 另 1 层压缩 KV 64，加上四层索引 16.25 + 3 × 8.125 | 128 | 104.625 |
| 合计 | 4 层历史 KV、4 层索引及 scale | 384 | 360.625 |

设 G 为本 worker 的原生页号数。worker 分配一块连续存储，先放 G 份 A，再放 G 份 B，最后放 G 份 C。下图每列代表一个原生页号，三行在内存中首尾相接。调度器一次把整列交给一个缓存组。

```text
                    页号 0         页号 1         页号 2       …
A，每格 128 KiB     [    A0    ]   [    A1    ]   [    A2    ]
B，每格 128 KiB     [    B0    ]   [    B1    ]   [    B2    ]
C，每格 104.625 KiB [    C0    ]   [    C1    ]   [    C2    ]
```

例如页号 17 归历史组时，A17、B17、C17 一起存一块历史。页号 18 归某个 SWA 组时，A18、B18 分别存该组两层的环形窗口，C18 留空。单层窗口和单层压缩器都需要完整 128 KiB，均只使用 A 或 B。历史页用尽三段空间，状态页仍有空余。

## 分组、配额与释放

一份历史使用一个原生页号。40 层 SWA 两两一组，每请求取 20 个页号。3 层 C2 分两组，每请求取 2 个页号，末组仅使用 A。全部 23 个缓存组共享同一个原生 BlockPool。窗口和压缩器分别持有自己的配额；请求被移出调度表后，底层引用仍存活的页继续计入配额。

令 S、C 分别为配置的窗口槽数与压缩器槽数。每个槽覆盖一条请求在全部对应层上的状态。启动预算换算和运行时接纳使用同一套计数。

- 每个原生页号对应 369,280 字节。可用持久缓存容量除以此值向下取整得到 G；池中有一个公共 null 页号。
- 历史可用块数为 G − 1 − 20S − 2C。接纳一条 700,001 输入的请求需要 5,469 块历史、一个窗口槽和一个压缩器槽。
- 时间顺序工作区、页表和 Mooncake 对齐用的空间需另行核算。CPU storage 统计对所有视图按底层指针去重。
- 关闭打包开关可在下次启动时回到统一步长版。P、D 须选同种布局，各端的 G、S、C 可以不同。当前实验使用部署配置保证两端一致。

## Pull 如何寻址

层描述符给出所在段、段内偏移和该段的页距。对页号 b，分量地址为「段基址 + b × 段页距 + 分量偏移」。例如 P 从 C17 发送索引，D 可写入 C31；P 和 D 各自使用注册元数据中的基址与本端页号。索引和 scale 保持各自的类型及分量描述。一个层的视图在页号维上的长度始终为 G，原版 Pull 得到的块缩放比例为 1。

P 在 N−1 处交接时提供各组源页号，D 用各组目标页号接收。接收所需的握手、选源和地址计算均使用原版 Mooncake Pull。减少存储步长节省的是持续驻留的 KV 字节；传输长度仍由有效分量决定。

## 收益与代价

| 每条请求、每个 worker | 统一步长版 | 候选版 |
| --- | ---: | ---: |
| 每个历史块 | 384 KiB | 360.625 KiB |
| SWA 和 C2 固定状态合计 | 5.375 MiB | 7.748 MiB |
| 700,001 输入的持久 KV 用量 | 2.008 GiB | 1.888 GiB |

700K 输入的历史部分省 124.84 MiB，固定状态多占 2.37 MiB，每条每卡净省约 122.47 MiB。两种固定槽各预留 72 个、每卡持久 KV 预算取 13.23 GiB 时，两版可用历史块分别为 35,094 和 36,883。六条 700,001 输入同时驻留需要 32,814 块；六条都再生成 65,536 token 约需 35,886 块。该估算假设六条请求同时保持驻留，总预算固定。

### 不同长度与混合请求的 D 端接纳

CPU 复用同一冻结调度器，比较原生布局、统一步长逻辑池和本候选版。D/TP2 单副本，每卡 KV 预算 13.23 GiB，上下文上限 1,048,576，关闭前缀缓存，每批 token 预算 512。每次冷交接先为 N−1 个外部 token 分配，再为最后一个本地输入分配。下面的字节数由空闲物理页号减少量乘以每个页号的成本得到。每种布局最多保留 72 条；以顺序到达的下一条无法分配或达到 72 条为止。K 表示 1,024。

| 输入 token | 每条每卡持久 KV（MiB），原生／统一／打包 | 同时接纳（条），原生／统一／打包 |
| ---: | --- | --- |
| 128 | 6.19 / 5.75 / 8.10 | 72 / 72 / 72 |
| 129 | 11.86 / 6.12 / 8.45 | 72 / 72 / 72 |
| 1K | 9.80 / 8.38 / 10.57 | 72 / 72 / 72 |
| 4K | 22.18 / 17.38 / 19.02 | 72 / 72 / 72 |
| 16K | 71.71 / 53.38 / 52.83 | 72 / 72 / 72 |
| 32K | 137.74 / 101.38 / 97.90 | 72 / 72 / 72 |
| 64K | 269.80 / 197.38 / 188.06 | 50 / 68 / 72 |
| 128K | 533.92 / 389.38 / 368.37 | 25 / 34 / 36 |
| 256K | 1062.17 / 773.38 / 729.00 | 12 / 17 / 18 |
| 700,001 | 2832.12 / 2056.25 / 1933.78 | 4 / 6 / 6 |

两种逻辑布局相较，每请求的固定成本和随 token 数增长的成本方向相反。设 H = ceil(N / 128)，打包版比统一步长版每条多用 (2,429.75 − 23.375 × H) KiB。N = 13,184 时统一版仍略省，N = 13,185 时打包版开始略省。该交点只适用于这两版在当前缓存几何下的持久 KV。原生窗口按页分配并可回收，128 和 129 两行就能看到相对原生的结果随页边界变化。单条用量较少也未必能再接一条请求。

两组混合输入采用固定次序循环，作为敏感性对照。每 7 条 4K 后面跟 1 条 256K，三版均达到 72 条。若 4K、64K、256K 各来一条循环，三版依次驻留 30、41、44 条。实际业务中各长度占比、等待和完成顺序、输出增长都会影响结果。上述数字属于 CPU 接纳计数。[复现用例](../../../../tests/ut/core/test_dsv41_resident_lengths.py)

## 验证范围

CPU 用例从平台 builder、实际 MRV2 张量视图和原生调度管理器进入。测试独立核对物理 storage 字节、历史与固定配额、128／129／257 三个交接边界的逐分量载荷及相邻请求保护。Pull 生成的地址由 CPU 内存拷贝执行。

CPU 调度器在 13.23 GiB 的同预算对照中，两版都接住六条 700K，第七条均被拒绝。随后为这六条请求分别再申请 65,536 个位置，候选版全部获批，统一步长版用尽历史配额。这一步验证了空间能否分出；实际生成是否达到相同长度、抢占次数及 TPOT 需要由服务测量。

A3 尚需用相同 W4A8 权重和独立参考对比完整词表概率，核查两端各 rank 的 SDK READ、DMA 完成以及取消后的安全复用，测量启动 HBM 和 TPOT。A3 性能对照应先按实际输入、输出和同时驻留的长度分布选负载，覆盖短请求页边界、中等长度高并发和长短混合。通过相同配置的官方 proxy 和 vLLM bench 对照 TTFT、TPOT、吞吐、排队、抢占与实际 P/D 并发。P 端应单列 prefill 计算与窗口整理的开销。六条 700K 持续生成可作为额外的长上下文压力项。表中的 CPU 驻留数不能用于推算服务吞吐。
